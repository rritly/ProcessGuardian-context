> **Current amendment notice — v2.5 (2026-11-02):** This file retains the complete v2.4 FINAL baseline below and appends the v2.5 amendment at the end. The v2.5 amendment is authoritative where it explicitly overrides v2.4, especially the elevated recovery policy (automatic task removal; no A/B UI), status/log-only presentation, standard Toast set, and autostart rollback transaction. All other v2.4 requirements remain in force. `SPEC.md` remains protected and must not be edited during this stage.


1. **C+D ship together.** Today `LoadAsync` returns the cached `AppSettings` instance and `SaveAsync` stores that same instance. There is no stale copy to resurrect `enabled=true`; the live bug is unsynchronized mutation of one object (path, pin, flag) by the orchestrator and the VM. Independent copies without a single writer create the resurrection bug. The store-copy contract and the controller therefore land in **one commit** (`C+D`). A commit that introduces the controller while the store still hands out the live instance is not allowed.
2. **Pin clear is on a committed path change only.** In the stopped state the controller clears the pin when the path is committed (Browse result, or the path text box losing focus / an explicit commit). A per-keystroke `PropertyChanged` must not clear the pin and must not schedule a save of a half-typed path.
3. **Owner of a trusted elevated data object is only `BUILTIN\Administrators` (`S-1-5-32-544`) or `LOCAL SYSTEM` (`S-1-5-18`).** The creating user's SID is not trusted, even if that user is an elevated administrator and the DACL is already hardened. New objects must receive one of those owners in the create security descriptor. The general rule remains: do not change owner/DACL of an untrusted config object before isolating it. **Narrow parent-container exception:** because the legacy `%ProgramData%\ProcessGuardianAdmin` directory contains sibling roots and must not be quarantined, A may re-owner/re-harden this *container only* through the handle-pinned protocol in A’s “Parent-container bootstrap” section, before any child is opened or read. `SeRestorePrivilege` may be enabled only for creating a protected object or this exact parent-container repair; it must never be used against `config`, `settings.json`, `.tmp`, `logs`, or a child about to be quarantined. Do not use `SeTakeOwnershipPrivilege` to take ownership of an existing child. Current elevated installs with a creator-owned parent are migrated through that narrow protocol; their old config is still independently quarantined once. A second start on a parent/config created and verified by this build must not repeat repair or quarantine.
4. **File-create model is (a) only.** `settings.json` and `settings.json.tmp` are created with an explicit protected security descriptor. `File.WriteAllTextAsync` / `File.Create` without that descriptor, followed by a later `HardenFile`, is not an acceptable implementation — that is the current `SaveAsync` race, and A includes it, not only `InitializeAsync`. Model (b) "verify inheritance after a default create" is withdrawn.
5. **Recovery journal is a seam, with a fixed key.** Interface `IElevatedRecoveryJournal` (in-memory fake in CI). Production key: `HKLM\SOFTWARE\ProcessGuardianAdmin\Recovery`, value `State` = `RecoveryInProgress` | `ResetNoticePending` (absent = complete). If the journal cannot be written, Error guidance names that key and says an administrator must repair its ACL or delete the value; the app does not touch untrusted config and does not pretend initialization succeeded. Quarantine directory names are `quarantine-<utc-ticks>-<n>`, not second-resolution timestamps.
6. **A full restart window is visible.** It does not set `Error` and does not leave a downed target looking like plain `MONITORING`. Status stays in the session set, `Restarting` is not entered, `IsDegraded=true` with a stable reason (`RestartDeferred`). Window timestamps live on the long-lived `GuardianOrchestrator` singleton, not on the controller, a per-session object, or an object recreated per Start.
7. **Do not terminate a session because the target file has been missing for 120 s.** The open product question is closed: FR-16 stands. `T = 120 s`, `N = 2` only raises `IsDegraded`. Stop stays available. Only an explicit user action re-pins.
8. **Elevated logs are a sibling of config, not inside it.** `%ProgramData%\ProcessGuardianAdmin\config` (A quarantines this directory) and `%ProgramData%\ProcessGuardianAdmin\logs` (L). A never renames the parent or the logs directory.
9. **`DisposeAsync` does not save settings.** Today's `MainViewModel.DisposeAsync` always calls `SaveAsync`, and `App.OnExit` sets `IsMonitoringEnabled=false` again on user exit. Both are removed. Settings writes happen only in the shutdown coordinator (user Exit / user Stop / fatal), never in `OnExit`, and never on SessionEnding. That is what makes "unsaved debounced edits are lost on Windows shutdown" actually true — the in-memory object already holds the edit before the debounce fires, so a dispose-time save would persist it.
10. **Budget and `MainModule` facts the tests must encode (current code, not the desired end state):**
    - A missing exe never reaches `HandleMissingAsync`. `ProcessTarget.TryCreate` requires the file to exist, so the restart counter is **not** incremented; status is set to `Error` and the loop continues. The counter increment before hash/start happens only after `TryCreate` succeeded.
    - A file that disappears before the hash is today **fatal**: `VerifyTargetHashAsync` treats unreadable/`null` as mismatch, disables monitoring, and resets the counter. It does not "spend a try". The desired end state (non-fatal `Missing` / `ReadError`) is a behavior change from that fail-closed path.
    - Per-candidate `MainModule` access denial is swallowed and, if no readable candidate matched the path, `CheckAsync` returns **`NotRunning`** (duplicate launch). `Unknown` is returned only when `GetProcessesByName` itself throws. The required behavior — `Unknown` when at least one candidate is unreadable and none readable-matched — is a behavior change.
    - `GuardianStatus.Error` today does **not** mean the cycle exited. `CanStart` is true for `Error`, so a second Start re-pins while the old loop is still running. The session token, not the enum, decides whether a session is active.

## Decisions (locked)

- **Scope:** three implementation blocks — **Increment N (.NET 10 LTS migration) runs first, before Stage 1**; then Stage 1 = P1 security + reliability (A, B, **C+D**, K, E, F); then Stage 2 = P2 hardening (G, H, I, J) + additions (L, M). Grouping C/D/E/K + consistent F is never split across stages. **C and D are additionally one atomic commit** (see acceptance revision §1): store copies and the single writer appear together.
- **Architecture:** light version — orchestrator owns session state; VM delegates via an Application-layer controller; store = persistence only. Existing entry points are migrated to the new contracts already in Stage 1 (the full shutdown coordinator stays in G).
- **Path+pin during monitoring:** editing the target is forbidden from the moment a Start command is accepted (session begins); change requires Stop → Start. A **committed** path change in the stopped state **clears the pin** (routed through the field owner, the controller). Committed means a Browse result or the path field losing focus / an explicit commit — **not** each keystroke (`PropertyChanged` on the two-way text box). A half-typed path must not clear the pin and must not be saved.
- **Empty pin (elevated):** launch blocked until an explicit Start re-pins; non-elevated keeps the compatibility skip.
- **Restart time-window limit:** missing field → safe non-zero default; `0` = off, only when explicitly set. A full window defers the next automatic relaunch and surfaces `IsDegraded` / `RestartDeferred`; it does not terminate the session. Window timestamps/counters live only on the long-lived `GuardianOrchestrator` singleton.
- **Autostart on user Exit:** preserved as documented; `[preserve]`.
- **User Stop/Exit persistence:** the latest *committed* UI snapshot is merged by the controller in the same serialized settings write that sets `IsMonitoringEnabled=false`; the path textbox draft is excluded until committed. `DisposeAsync` and `OnExit` never save settings. Windows SessionEnding deliberately performs no UI flush.
- **Persistence:** **all** VM saves (including the 500 ms debounce and `FlushNowAsync`) go through the controller / merge service — no separate direct path to the store. The autostart reconciliation that today sits inside `FlushSaveAsync` moves with that merge; the VM does not keep a second writer. The controller is the single writer of session state (`IsMonitoringEnabled`, pin) and merges UI-editable fields atomically. The store caches the document internally and returns copies — no caller gets a mutable reference (neither from `LoadAsync` nor `SaveAsync`). `DisposeAsync` does not save.
- **Error semantics:** Error = a **terminated session** — the session is cancelled and the **desired `enabled=false` is set in memory**. `Save(false)` is **best-effort, error-handled**: on a save failure Error is still published (with a separate persistence-failure flag); the disk may then keep the old value — for this run the in-memory state is authoritative (see F for the recorded no-durable-latch limitation at the next launch). Unknown never terminates a session. **Consecutive-budget exhaustion is a fatal cause** (a full window alone only defers relaunch, per I). Notification failures never disable monitoring; user cancellation is never Error. Until F lands, `GuardianStatus.Error` is not treated as "no session" — today's loop keeps running after it sets Error.
- **Transient target-EXE disappearance:** degrade (show `IsDegraded`), don't error, and **do not terminate after 120 s** (the former open product question is closed; FR-16 stands). See E.
- **Elevated layout:** `%ProgramData%\ProcessGuardianAdmin\config` (settings; A may quarantine this directory) and `%ProgramData%\ProcessGuardianAdmin\logs` (logs; L), under `%ProgramData%\ProcessGuardianAdmin`. A must establish/verify the parent container using the handle-pinned bootstrap protocol in A before any child I/O. A may quarantine only `config`; it never quarantines the parent or `logs`. Parent hardening does not make any existing child trusted: `config` is independently verified/quarantined, and an untrusted pre-existing `logs` directory triggers L’s memory-only fallback.
- **Trusted elevated owner:** `BUILTIN\Administrators` or `LOCAL SYSTEM` only. See acceptance revision §3 and increment A.
- **Commits:** allowed per atomic increment; `SPEC.md`, `AGENTS.md`, `opencode.json` (and `.gitignore`) and this plan file are never staged or committed. C+D is one of those increments.

## UI state dictionary (mandatory for C, E, F)

The plan text previously referenced states that do not exist in the system ("Starting", a "warning state"). The closed set today:

- **Enum `GuardianStatus`:** `Stopped`, `Waiting`, `Monitoring`, `Restarting`, `Error` — **not extended** in this effort.
- **Converter `StatusToDisplayConverter`:** Waiting/Monitoring/Restarting → `MONITORING`, Error → `ERROR`, **any other/unknown value → `STOPPED`**.
- **XAML (`MainWindow.xaml`):** Start button collapsed when Status ∈ {Monitoring, Waiting, Restarting}; Stop button visible for the same set; status-text color triggers per enum value; an unknown enum falls back to the default (Stopped) styling.
- **Tray (`TrayIconService.SetStatus`, TR-03):** On icon for {Monitoring, Waiting, Restarting}, Error icon for Error, **everything else (incl. unknown) → Off icon**; tooltip `{AppEdition.Name} - {Status}`; menu toggle label from `_isMonitoring` = {Monitoring, Waiting, Restarting}.

**Preferred model (adopted):** the enum is **not extended** for transient/degraded situations. A **separate `degraded`/warning flag** (`IsDegraded`, a VM/controller property) sits beside the active session and is meaningful only while state is in the session set (Monitoring/Waiting/Restarting): it signals "state undeterminable too long / transient failure" (E, F) or "next automatic relaunch is deferred by the restart window" (I, reason `RestartDeferred`). It **never changes the enum value, never cancels the session, never renames the state**. Projection of the tuple `(Status, IsDegraded, reason)`:

- enum — unchanged (5 values);
- converter — unchanged mapping; the degraded/deferred reason is a **separate binding**, not a new enum label. The status row shows the reason text (for example "MONITORING (degraded)" or "relaunch deferred"), not only the enum word;
- XAML triggers — stay keyed on enum values; `IsDegraded` drives a separate warning element (text/tooltip), not the Start/Stop triggers;
- tray — icons unchanged; the tooltip includes the reason ("- Monitoring (degraded)" / "- Monitoring (relaunch deferred)") without a new icon asset (`[optional: dedicated warning icon deferred]`).

All wording in C/E/F/I uses only these states plus the explicit `IsDegraded` flag and a stable `reason` string — no "Starting", no "warning state" terminology. The reason is not optional: a degraded or deferred session with an empty reason fails review.

## Stage 1 — Elevated security + P1 reliability (A, B, C+D, K, E, F)

### A — [defect] Elevated config: quarantine-and-recreate instead of a trust marker
**Files:** `src/ProcessGuardian.Infrastructure/Configuration/JsonConfigurationStore.cs` (quarantine/recreate + non-fatal init), a small elevated ProgramData-root bootstrap/security helper, the elevated recovery/notice-state helper under Infrastructure (HKLM bookkeeping), `src/ProcessGuardian.Wpf/Bootstrapper.cs`, `src/ProcessGuardian.Wpf/App.xaml.cs`, and the minimum existing ViewModel/window/tray wiring required to show an ordinary Error/reset indicator; new `tests/.../ElevatedConfigFailClosedTests.cs` plus root-bootstrap and boot-path regression tests. A may add only the minimal startup/error route needed before the controller exists; C+D later migrates the steady-state monitoring status channel to `IMonitoringController` rather than creating a second long-lived state owner.

**Model replaced:** the earlier "trust marker inside settings.json" approach is **abandoned**. A marker inside a file the user could write to is forgeable (pin their own EXE + a forged "confirmed" marker), and write-over-a-weak-ACL-then-harden leaves a race window. **New model — quarantine and recreate.**

**Ordering note (dependency):** the single-writer contract (C+D) is no longer needed for untrusted-state persistence — the old content is quarantined and a **fresh** default config is written instead, so A no longer depends on the controller for persisting "monitoring off + pin cleared". A no longer has a persisted `RequiresTargetConfirmation` field and there is no transitional store-write of cleared state. Stage-1 sequence is **N → A → B → C+D → K → E → F** (C+D is one commit).

Three branches, no "safely disabled with a marker" state:

1. **Normal (trusted) — load, no quarantine/reset.** The existing configuration passes the protection check (owner is exactly `BUILTIN\Administrators` or `LOCAL SYSTEM`, hardened DACL, no reparse): it is **loaded as-is** with **no** quarantine or reset. The owner of the elevated user who happens to be running the process is **not** a trusted owner. The DACL check is a **normalized known-template comparison, not a universal effective-access analyzer** — it verifies three facts directly: **(1)** the required `Administrators`/`SYSTEM` rights are present, **(2)** there are **no foreign allow permissions** for any other SID, and **(3)** there are **no unexpected deny ACEs** (a deny ACE does not *grant* anything — the point is the absence of surprises that would shadow/deny the required rights or alter the expected ACL shape). **Test:** two consecutive starts on a config **this build created** preserve the settings (no spurious reset on the second run). **Test:** a strong DACL whose owner is the creating user SID is quarantined, not loaded. Existing installs (DACL hardened, owner left as the creator — that is what the code at `e07bc18` does) therefore reset **once**.
2. **Unsafe location — refuse I/O.** The location is unusable when a `ReparsePoint` attribute is present on the dir/file path, or **the untrusted object cannot be isolated safely from a verified protected parent** (a rename out of the way cannot be performed safely; **no attempt is made to "bring the owner to `Administrators`/`SYSTEM`" first** — a foreign owner is treated as untrusted, never as a fixable condition), or quarantine/recreate keeps failing (below). In this state the store **refuses to read and write** (dedicated exception; no settings object is returned). **Start cannot bypass the refusal.** The app reports Error with guidance; recovery happens outside the app.
3. **Any other config-subtree weakness — quarantine and recreate.** For the `config` directory and its settings files (the parent container follows the separate bootstrap exception above), every weakness — directory ACL, file ACL, or **any** foreign owner ("the owner *can* be corrected" is **not** a category for these config objects: a foreign owner is always untrusted) — triggers **quarantine-and-recreate** instead of in-place hardening of untrusted content:
   - The existing configuration (dir and/or `settings.json`) is **renamed into a quarantine** (sibling name `quarantine-<utc-ticks>-<n>`, unique across sub-second retries) **only — there is no "leave in place but never read" variant**; it is never trusted, hashed, migrated, or re-used for its pin/target. **Quarantined content is not read** (no migration, no parsing of the old pin/target from it). The quarantined object is the **`config` directory** (`%ProgramData%\ProcessGuardianAdmin\config`), never the parent `ProcessGuardianAdmin` directory and never `logs`.
   - A **new protected `config` directory** is created, **protected from the moment of creation** (born-hardened: inheritance disabled, hardened DACL, owner `BUILTIN\Administrators` or `LOCAL SYSTEM`), and a **fresh default** config is written into it: **monitoring off, empty pin**. The security descriptor passed to the create call includes that owner. If the API requires a privilege to set an owner different from the caller, enable `SeRestorePrivilege` only for this create operation. Do not enable `SeTakeOwnershipPrivilege` as a substitute for setting the required Administrators/SYSTEM owner. If the platform/API path cannot create the object with the required owner and descriptor, fail closed; never create permissively and harden afterwards. Privilege adjustment against an existing untrusted config object is not allowed. A created directory whose owner is still the user SID fails post-create verification and is not used.
   - **Target confirmation is provided by K, not by any marker:** the empty pin in the elevated edition **blocks launch** until an explicit Start re-selects/re-pins (K policy) — the user re-confirms the target interactively. No persisted `RequiresTargetConfirmation` field exists; there is **no transitional store-write** of cleared state.
   - **No owner/DACL change to the untrusted object before isolation — so no `TakeOwnership` of it at all.** The untrusted object's owner/ACL are **never modified** before it is moved out of the way (a takeover that flips ownership then crashes would leave the old content looking trusted before quarantine completes). `TakeOwnership` is **not used as "only inspection"** either — the owner is read (read-only attribute query, which needs no privilege), and any foreign owner immediately classes the object **untrusted**. If the untrusted object cannot be isolated safely, it is a **refusal + manual recovery**, never an incomplete takeover that could bless old content.
   - **Isolation is by rename from a verified protected parent, not recursive delete.** The safe isolation is **renaming** the untrusted object out of the way, performed **from a verified trusted/protected parent path**; there is **no automatic recursive deletion** of an untrusted directory tree (that could destroy unrelated user content). If no verified protected parent for the rename operation can be established, that is an **unsafe-location** refusal (branch 2), not a forced operation.

**Close the recreate race (create-exclusive + post-create verification).** Ordinary users can create subdirectories under `%ProgramData%`, and `DirectoryInfo.Create(DirectorySecurity)` / `Directory.CreateDirectory` **silently succeed if the directory already exists without applying the ACL** — so an attacker could create `ProcessGuardianAdmin` first in the quarantine→create gap (including on the very first run on a clean system). Requirements:
- **The create must fail if the object already exists:** use `CreateDirectory` + check for `ERROR_ALREADY_EXISTS` (P/Invoke `CreateDirectory` or a create-exclusive API) — an already-present object is treated as a collision, **not** a silent success.
- **Create-exclusive receives the required security descriptor at creation:** the born-hardened DACL + owner are supplied **as part of the create call** (in the `DirectorySecurity`/security-descriptor of the creating API), not applied afterwards by a second mutation — so a freshly created object is born correct, never created permissive then fixed.
- **Mandatory post-create verification:** after creation, verify the **owner and DACL** of the created directory/file (per the fresh-config check above); a created-but-not-verified object is unusable.
- **Bounded retries:** on "already exists" or a failed post-create check, isolate (rename) and re-create up to a **bounded number of retries**; if it still collides or fails verification, escalate to the **unsafe-location** refusal. Applies to first run on a clean system too.
- **`settings.json` / `settings.json.tmp` are created with an explicit protected descriptor (model (a) only).** Model (b), "create with the default ACL and then verify inheritance", is **withdrawn**: `File.WriteAllTextAsync` + a later `HardenFileForAdministratorsOnly` is the race A exists to close, and it is the current `SaveAsync` implementation. A covers **every** create path — `InitializeAsync` **and** `SaveAsync` — not bootstrap alone. The temp file is created (create-exclusive, descriptor attached) inside the verified `config` directory, written, and `File.Move`d over `settings.json`. Both the temp file and the replaced `settings.json` must pass the owner/DACL check before the save is treated as committed. A file that exists only with a default or inherited-Users ACL is untrusted even if a later harden call is about to run.

**Edition scope — `ELEVATED_EDITION` only.** All of A's logic (quarantine, recreate, verification, refusal) applies **only in the elevated edition** (`ELEVATED_EDITION` define, `ProcessGuardianAdmin.exe`). The regular edition's user-scoped config (`%LocalAppData%`) is not subject to A.

**Layout migration from `e07bc18`.** Today the elevated file is `%ProgramData%\ProcessGuardianAdmin\settings.json` (no `config` subdirectory). A does **not** rename the parent directory. On first run, a parent-level `settings.json` (and a parent-level `settings.json.tmp`) is quarantined by **rename of that file only** — never read, never hashed, never copied into `config`. Then `config\` is create-exclusive with the trusted owner and receives fresh defaults. A leftover parent-level `settings.json` that is still the live path fails review.

**Parent-container bootstrap — mandatory prerequisite for A and L; do not confuse the container with trusted settings.** The parent `%ProgramData%\ProcessGuardianAdmin` must itself have a trusted owner (`BUILTIN\Administrators` or `LOCAL SYSTEM`), a protected DACL, disabled inheritance, no reparse indirection, and permissions that prevent non-admin replacement/rename/creation of its protected children. `ProgramData` and the resolved parent path/ancestor chain must be checked before opening any child. The parent's DACL alone is insufficient because a non-trusted owner can alter it.

- **Clean first run:** create the parent exclusively with the protected descriptor and trusted owner at creation, then verify the owner, DACL, reparse state, and path identity. An object-already-exists result is a collision, never a successful create.
- **Existing legacy parent:** the current code may have left the creating user's SID as owner even when the DACL looks hardened. The parent is a namespace/container, not the source of target settings; because A must preserve the sibling `logs` root and must not quarantine the parent, the only allowed in-place repair is a narrowly scoped, handle-based bootstrap. Open the parent relative to a verified `%ProgramData%` anchor with no-follow/reparse-safe semantics and a directory handle whose share mode excludes write and delete/rename access while the repair is performed (for example, a `CreateFile` directory handle with `FILE_FLAG_BACKUP_SEMANTICS`; fail closed if conflicting handles prevent opening it). Keep the handle open while setting the trusted owner and protected DACL, then verify the same volume/file identity still resolves at the expected path and post-check its owner, DACL, inheritance, and reparse status. Do not infer that changing the parent DACL revokes access already granted to an existing child handle; independently quarantine/verify each child before use. Apply `SeRestorePrivilege`, if necessary, only to this parent directory handle for this repair; do not use it to alter a child object.
- **Fail closed if identity cannot be pinned.** If the existing parent is a reparse point, path/ancestor checks are ambiguous, a conflicting handle prevents obtaining the required non-replaceable handle, owner/DACL cannot be verified, the security descriptor cannot be applied, or the post-check fails, refuse file I/O and show ordinary Error guidance for manual administrator recovery. Do not fall back to opening child paths by name and do not repair an uncertain parent by recursive deletion or rename.
- **Parent hardening is not child trust.** Do not read, parse, hash, or open legacy `settings.json`, `settings.json.tmp`, `config` contents, or any log file until the parent is verified. Afterward, A independently quarantines/recreates an untrusted `config` child and never reads its contents. L independently verifies `logs`; if an existing `logs` directory or its pre-existing files do not meet L's trust/clean-location rule, L uses memory-only logging rather than trusting, re-owning, or importing those files. A never quarantines the parent or `logs`.
- **Repeat-start behavior:** on the next start, a parent created or successfully repaired by this build passes verification without another ownership mutation or quarantine. A legacy parent may be repaired once; the legacy settings file itself is still quarantined by rename and never read.

**Parent bootstrap tests:** clean create is born-protected; legacy user-owned parent with otherwise strong DACL is repaired only through the handle-pinned parent path, without opening/reading children first; the second start makes no repair/quarantine; reparse, path-identity swap, inability to exclude replacement, or failed post-verification causes refusal before child I/O; the `config` directory and every file still undergo independent verification; an untrusted `logs` directory leads to memory-only logging and is never renamed by A. Manual elevated verification includes the parent owner/DACL and a non-admin replacement attempt.

**HKLM recovery/notice state — persistent bookkeeping, never a trust gate.** The elevated edition uses a dedicated application-owned HKLM state. **Key (fixed):** `HKLM\SOFTWARE\ProcessGuardianAdmin\Recovery`. **Value:** `State` (`REG_SZ`) = `RecoveryInProgress` or `ResetNoticePending`; absent means complete. The key is created with a restrictive ACL (owner `BUILTIN\Administrators` or `LOCAL SYSTEM`, inheritance disabled, FullControl only for those two SIDs) and its owner/ACL must be verified before relying on it; a pre-existing weak or unverifiable key must not be silently accepted. If the journal cannot be secured/read or a required state transition cannot be persisted, refuse the affected recovery and surface the ordinary Error path rather than touching untrusted config or silently losing the notice. **The Error text names this key** and says an administrator must repair its ACL or delete the value; a generic Error with no escape hatch fails review. The journal records recovery progress and notice acknowledgement only. It **never** makes a config trusted, never suppresses the per-launch owner/DACL/reparse checks, and never authorizes a target launch. A marker state may force more conservative recovery or refusal, but must never weaken verification.

**Journal seam.** Production code talks to `IElevatedRecoveryJournal`. CI uses an in-memory fake so "crash at each step" does not require an elevated runner. The real HKLM key is on the manual elevated checklist, not a CI gate. The ACL/owner decision logic is unit-tested through a seam that accepts fabricated security descriptors; CI does not claim to have proved a live DACL.

- **Crash-safe ordering:** after deciding that an existing config is untrusted, persist `RecoveryInProgress` **before** renaming or modifying any config object. If this state cannot be written, refuse the recovery without touching the config and surface the ordinary Error path. While `RecoveryInProgress` is present, do not load, parse, hash, or migrate the current settings; resume quarantine-and-recreate. Only after fresh defaults have been written and the directory, `settings.json`, and applicable `.tmp`/replacement files have passed the protection checks may the state transition to `ResetNoticePending`. If that transition fails, initialization remains refused and the next launch resumes recovery; do not silently report a successful initialization. This makes the marker a conservative recovery journal, not proof that an object is safe.
- **User-visible reset notice — pending until the user resolves it.** After quarantine-and-recreate, the user must see a persistent indicator (per the UI state dictionary / J) that the target path, numeric settings, and `AutostartEnabled` were reset. The fresh config starts with monitoring off and `AutostartEnabled=false`; **a pre-existing scheduled task is left alone at reset time**. The pending state survives restart and is surfaced in the status row/tray tooltip independently of `EnableToasts`; a one-shot toast is insufficient.
- **Explicit task/flag resolution:** the user chooses **(a) keep the scheduler task and re-enable `AutostartEnabled`**, which requires explicit target re-selection/re-pinning and successful persistence of the chosen settings, or **(b) remove the scheduler task and keep `AutostartEnabled=false`**, which requires successful task removal and successful persistence of the disabled flag. Until the selected action and its required persistence steps succeed, `ResetNoticePending` remains set and the mismatch is surfaced; no automatic task deletion or autostart re-enable is allowed. A failed action is retryable and must not clear the pending state.
- **Acknowledgement ordering:** clear the pending notice only after the selected option's required operations have succeeded. The operations must be idempotent so a crash during resolution can be retried without silently reversing user intent.
- **Old untrusted settings are never read or migrated:** values displayed after reset come from fresh defaults; the quarantined content never supplies the target, pin, numeric settings, autostart flag, or notice state.

**Bootstrap-write exception.** Writing fresh default settings during `InitializeAsync` (quarantine/recreate) and advancing the HKLM recovery/notice journal are explicit bootstrap exceptions to the controller-single-writer rule (D): no session/controller exists yet, and these are security-mandated recovery operations, not UI saves. After initialization, all user-driven changes to `IsMonitoringEnabled`, target path, pin, autostart flag, and acknowledgement of `ResetNoticePending` must use the controller/merge contract; the recovery helper must not become a parallel general-purpose settings writer.

**Why not a settings-file trust marker or write-then-harden:** a marker inside the untrusted settings file is forgeable (a user could pin their own EXE and forge confirmation), and writing over a weak ACL then hardening leaves an unattended race window. Deleting/recreating the object removes untrusted content instead of carrying it forward. The HKLM state above is only a crash-safe recovery/notice journal; actual object protection is verified at every launch, and launch authorization remains governed by K and the edition-specific pin policy.

**Test — crash at any step of quarantine/recreate:** forcing a failure at each step (journal write, quarantine rename, quarantine isolation, directory create, default write, post-create verification, `ResetNoticePending` transition) must **never yield a trusted-looking config with the old pin**; the outcome is Error/refusal, resumable `RecoveryInProgress`, or clean born-hardened defaults with monitoring off and empty pin. If the journal cannot be written, no untrusted config object is touched. A crash/restart while `RecoveryInProgress` resumes recovery without reading the quarantined/current config content. **Test — strong-DACL dir with a foreign owner is rejected** (quarantined/recreated, not accepted as trusted). **Test — recreate race:** the directory appearing between quarantine and create (simulated collision / `ERROR_ALREADY_EXISTS`) ⇒ the config is **not used** — bounded retries, then unsafe-location refusal; never silent ACL-applying success. **Test — normal branch:** two consecutive starts on a clean protected config preserve the settings (no spurious reset). **Test — rename-only isolation:** quarantine is a rename (never a leave-in-place variant) and the quarantined content is never read back. **Test — pending reset notice:** `ResetNoticePending` survives restart until the user selects and successfully completes an explicit resolution; failed task removal/settings save does not clear it; **no auto-delete of the scheduler task and no auto re-enable of `AutostartEnabled`** occur without the user's explicit choice; a crash during resolution is retryable/idempotent; old untrusted settings are never the notice's source.

**UI behavior for refusal and `--background` boot (`[links to C/J]`):** a refused `LoadAsync` or failed `InitializeAsync` in the unsafe state must **not** reach the fatal `MessageBox` of `App.OnStartup` (EH-03) and must not terminate the process merely because the store could not initialize. It is an ordinary Error path with guidance; for `--background` startup, surface it through tray icon/tooltip/persistent indicator without stealing focus or opening a MessageBox. Repeated **write** refusals (Save) degrade to the same Error path with a retry hint. A provides the minimum boot-path wiring before the controller exists; C migrates this state to the controller DTO channel, and J improves visibility of persistence/autostart failures.

**Constructor does I/O today — must become a non-fatal init path.** `JsonConfigurationStore` currently performs I/O and hardening in its constructor, so an exception while creating the service would propagate into `App.OnStartup` and trigger the fatal `MessageBox` + shutdown **before** any Error UI (EH-03). The constructor builds only the in-memory resolver and holds no handle/data; all file, ACL, registry recovery-journal, and quarantine work runs through explicit initialization. The boot path catches initialization failures and routes them to the ordinary Error UI/tray state without relying on a successfully initialized store or controller. The orchestrator must not start and no monitoring launch may occur until initialization either completes successfully or the app enters the ordinary refusal/Error mode. **Tests:** force both service-construction and `InitializeAsync` failures; confirm the ordinary Error path, no fatal `MessageBox`/process shutdown, no monitoring loop or target launch, and correct `--background` tray-only behavior.

**Correction steps:** protection check on dir/file — reparse present on the object **or** on any verified-path ancestor, or the untrusted object **cannot be safely isolated from a verified protected parent**, or quarantine/recreate keeps failing → **unsafe location** (refuse I/O); any owner/DACL weakness → **quarantine-and-recreate**: rename the existing object into quarantine **from a verified protected parent** (owner/ACL of the untrusted object **never modified** first), create a born-hardened directory (inheritance disabled, hardened DACL supplied at create, owner `Administrators`/`SYSTEM`), write fresh defaults (monitoring off, empty pin). **`TakeOwnership` is never used before isolation** — not to inspect/decide, not to bless content; ownership is *read* (no privilege), and any foreign owner means untrusted + quarantine, per branch 3. If the verified parent path for the rename cannot be established (reparse/trust check fails), escalate to the unsafe-location refusal.

**Fresh-config protection check (the created file/dir, not migrated content):** a **normalized known-template** check, not a general effective-access analyzer — owner is exactly `BUILTIN\Administrators` or `LOCAL SYSTEM` (the creating user SID fails the check), existing non-empty DACL present, inheritance disabled, required `Administrators`/`SYSTEM` rights present, **no foreign allow permission for any other SID**, and **no unexpected deny ACEs** (deny ACEs do not grant; the check looks for surprises that shadow the required rights or alter the expected ACL shape) — a property/shape check, not exact-list equality. **If the owner or DACL cannot be read (`READ_CONTROL` denied), the check fails closed** → unsafe-location refusal (never "unknown → proceed").

**Trusted parent/ancestor verification — replaceability, not admin-only-DACL-everywhere.** Ancestors are verified to confirm the **app-root and its objects cannot be substituted/renamed/created by a non-admin** (so the app-root path is not a link to, or shadowed by, a user-controlled object) — it is **not** required that every ancestor up to the drive root carry an admin-only DACL. For the elevated edition, this includes the explicit parent-container bootstrap above: the `%ProgramData%` anchor and any path segment that could divert the app-root are checked; the `ProcessGuardianAdmin` parent is handle-pinned and post-verified before child I/O; a non-admin must not be able to replace/rename the parent or create/replace protected children after bootstrap. A parent reparse or an unverifiable upper segment that could divert the derived path is an **unsafe-location refusal**. Missing or ambiguous upper-segment rights do not fail a healthy root merely because they are not admin-only.

**`settings.json` / `.tmp` protection model — explicit descriptor only.** Model **(a)** is required: each file is created with the born-hardened DACL and a trusted owner (`BUILTIN\Administrators` or `LOCAL SYSTEM`), with no window in which the file exists under the creator's default ACL. Model **(b)** (create first, verify inheritance afterwards) is withdrawn. The common protection check — normal branch and fresh-config — verifies that explicit descriptor. A file is never trusted because its parent directory is trusted.

**Boundary honesty:** `settings.json.tmp` (the `SaveAsync` temp+rename path) and file replacement are inside the protected directory; the location check and the later read/use of a path are not one atomic operation — attribute/ACL checks **narrow** file races, they are not claimed to eliminate all of them. (Quarantine/recreate removes untrusted *content*; path-selection races remain narrowed, not eliminated.)

**Real-ACL verification:** unit seam covers logic; a separate **manual Windows/elevated verification pass** (both editions' real locations) validates actual DACLs and ownership. The checklist is concrete, not "documented later":

The parent bootstrap must hold/pin the same directory identity through owner/DACL repair and post-verification.
- Second start does not create a `quarantine-*` sibling.
- A `config` directory pre-created by a non-elevated user is not loaded; it is quarantined or the location is refused. Its owner and DACL are unchanged before isolation (no `TakeOwnership` on it). A legacy user-owned **parent container** is the narrow exception: it may only be repaired through the verified, non-replaceable parent-handle protocol; if that protocol fails, no child I/O occurs and the app refuses initialization.
- During `SaveAsync`, `settings.json.tmp` never shows a Users modify ACE. Sample the ACL after the create returns and before `Move`, via a test seam if a live race cannot be frozen.
- `HKLM\SOFTWARE\ProcessGuardianAdmin\Recovery` and the sibling `logs` directory have the expected trusted-owner/ACE shape. A weak or unverifiable journal key is not used; an untrusted `logs` directory is not renamed or opened and causes memory-only logging.
- `--background` refusal shows the tray indicator and does not open a MessageBox.

CI runs non-elevated and cannot prove this checklist.

### C+D — [defect] Session-scoped cancellation, controller single writer, and independent copies
**Files:** `GuardianOrchestrator.cs` (+light `IMonitoringController` in Application), Domain (new immutable `SessionSnapshot`), `JsonConfigurationStore.cs`, `MainViewModel.cs`, `Bootstrapper.cs`, `App.xaml.cs` (entry-point migration only), `GuardianOrchestratorTests.cs`, `JsonConfigurationStoreTests.cs`

**One commit.** The controller (this section) and the store-copy contract (the former D section) ship together. Do not commit a controller that still reads and writes the shared `AppSettings` instance `LoadAsync` returns today.

The orchestrator owns a per-session `CancellationTokenSource`; the controller **serializes Start/Stop internally** (a controller-level lock/queue — the UI busy gate is no longer the only guard). The typed result distinguishes `RuntimeStopped` from `SettingsSaved`; the controller must never report a successful Stop unless `RuntimeStopped=true`. Cancellation synchronously closes the launch gate before the first asynchronous wait. A `CancellationToken` check alone is **not** sufficient to guarantee that no launch races with Stop.

**Launch-gate linearization with `Process.Start` (mandatory).** Path validation and asynchronous hashing may occur outside the gate, but after they complete, the last session-identity/token/gate check and the synchronous `Process.Start` call must execute in one non-awaiting critical section coordinated with `StopAsync`/`SuspendAsync`. Stop/Suspend use the same synchronization primitive to close the gate and cancel the session. If Stop closes the gate first, the pending launch is rejected. If a launch critical section wins first, Stop must wait for that synchronous `Process.Start` section and the session task to settle before reporting `RuntimeStopped=true`; no `Process.Start` may begin after Stop has closed the gate, and none may occur after a completed Stop returns. Do not hold a lock across `await`; do not rely on a token check outside the synchronized section. Stop stops the guardian session; it does not imply that a target process already launched is killed. A timeout/failsafe must keep the gate closed and must not allow a replacement session while the old launch/session operation is still in flight.

**Today `Error` is not "session over".** `RunMonitoringCycleAsync` sets `GuardianStatus.Error` when `CheckAsync` throws and when `ProcessTarget.TryCreate` fails, then keeps looping while `IsMonitoringEnabled` stays true. `CanStart` is true for `Error`, so another Start re-pins under the still-running loop. The session CTS is the source of truth. The Start gate treats "a session task is still running" as busy even if the published status is already `Error`. F later stops those paths from publishing Error; C+D must not wait for F to close the re-pin hole.

- **Controller contract (Application layer, `IMonitoringController`):** `StartAsync(...)` accepts a Start request; `StopAsync(CommittedSettingsSnapshot? latestCommittedSettings = null)` cancels the session and attempts to persist `IsMonitoringEnabled=false` (user Stop / user Exit). UI-originated Stop and Exit pass a frozen snapshot of the latest committed UI-editable fields; non-UI callers may omit it. The immutable snapshot excludes a target-path draft not yet committed and never supplies controller-owned `TargetHashSha256` or `IsMonitoringEnabled`. Under one controller serialization boundary, Stop closes the launch gate, cancels/awaits the session, merges the supplied committed fields (when present) with controller-owned state, sets `IsMonitoringEnabled=false`, and performs one final store save. `SuspendAsync()` cancels the session **without** persisting the flag or UI snapshot (used by G for Windows SessionEnding). A completed Stop returns a typed `StopResult` with separate `RuntimeStopped` and `SettingsSaved` outcomes plus an optional persistence error; do not encode both guarantees in one success boolean. The controller must not report a successful Stop unless `RuntimeStopped=true`. `SettingsSaved=false` means desired `enabled=false` remains authoritative in memory for this run, `SaveFailed` is surfaced, and the UI must not label the whole operation as fully successful. This result does not claim a durable off-state if the save failed (F's accepted limitation). `SuspendAsync` closes the launch gate/cancels synchronously before its first await, never writes the flag, and is the Stage-1 contract G consumes in Stage 2. Before final Stop/Exit persistence, the VM freezes the edit stream and cancels future debounce scheduling; the controller seals that UI-save generation so a late stale debounce operation cannot write after the final snapshot save or after teardown.
- **Start order (controller computes the pin):** **1)** validate the path form and require an existing readable file (per E — reject otherwise, no session); **2)** compute the canonical path and target hash/pin — **the pin is computed by the controller** (K), not supplied/stored by the VM; **3)** persist **canonical path + pin + `IsMonitoringEnabled=true` together, consistently**, **before** the session starts; **4)** take the session snapshot; **5)** begin the check loop. **A failed save does not start monitoring** (a Start whose pin/enabled persist fails → no loop, session not engaged). Two separate pin/enabled writes are **not** required — the atomic controller merge covers both; consistency of stored + snapshot, not two disk calls, is the guarantee. The `IsBusy` gate (next bullet) spans steps 1–5 and re-opens once the loop is stable.
- **Controller rejects target changes during an active session (beyond UI lock):** changing the target while a session is active is rejected **at the controller level**, including changes arriving via a **late debounced save** (a stale UI snapshot carrying a new target). A single read-only UI lock is **not sufficient** — the controller (single writer) must ignore/reject any merge that would change the target path mid-session, so a stale debounced save can never retarget a running session. (Path change effective only in the stopped state, per Decisions.)
- **Application → UI state channel (DTO/event), not direct VM mutation:** the controller exposes a state channel (event/`IObservable` of a `MonitorState` DTO: `Status`, `IsDegraded`, `reason` string, and a **`SaveFailed` flag** surfaced separately from `Status` — per F, an Error is published even when `Save` itself failed) that the VM projects onto `GuardianStatus` + `IsDegraded` bindings. This decouples the orchestrator from the VM and keeps the UI state dictionary (above) authoritative. **The degraded indicator is surfaced independently of `EnableToasts`** — a persistent degraded state (E/F) must remain visible in the status row/tooltip whether or not toast notifications are enabled.
- **Operation/busy state:** a separate `IsBusy`/operation gate blocks path/pin editing **from the moment a Start request is accepted** and while pin/snapshot are computed and saved (K, steps 1–5 above), staying latched until the controller returns or the session reaches a stable state. This is the controller-visible counterpart of the failsafe below.
- **Stop during a pre-session Start (hash/persist still in flight):** the controller must treat Start as an in-flight **pre-session operation** and make Stop capable of acting on it — either **(a)** a dedicated **cancel of the pending Start** (discard the pre-session work: cancel hash/pin computation and any not-yet-committed persist) or **(b)** **serialize/wait** — Stop waits for the pending Start to finish, then immediately stops, with **explicit UX** (the user sees one definite outcome, not two racing commands). Both are controller-level, not a UI gate alone. **`RuntimeStopped` and `SettingsSaved` are separate guarantees:** if the Start's persist already committed `true` before Stop was received, the Stop completes the same serialized transition by attempting to persist `false` — **when that save succeeds, no `enabled=true` remains on disk**; **if the revert save fails, the returned `StopResult` has `RuntimeStopped=true` and `SettingsSaved=false`, the in-memory desired state is `false`, `SaveFailed` is surfaced (J), and the disk may retain `true`** (no-durable-latch limitation, per F) — the runtime is still stopped and the UI does not report full success. If the persist never committed, the pre-session work is simply discarded. **A late-completing Start can never launch the target after Stop returned** — the launch gate is cleared/aborted with the pending work.
- **Fatal-error flow without self-await/deadlock:** the orchestrator itself **exits the cycle loop first** and *then* reports Error (no `await` of the session task from within the loop — that would self-await/deadlock). On a fatal cause the controller **attempts to persist `IsMonitoringEnabled=false`** (best-effort, error-handled) **and publishes Error even if the save fails** (with a separate save-failure flag on the state DTO, per F); the UI observes Status=Error through the state channel and shows the Error screen; the Start gate re-opens only after the in-flight session actually ended (failsafe).

- **Failsafe:** may request cancellation of the stuck session but **must not allow a new session until the old one has actually finished** — the gate re-opens only after the in-flight operation really ends.
- **Stage-1 migration:** existing entry points (tray Start/Stop, App exit path, boot-time load) call the new controller contracts; the full shutdown coordinator remains G's scope.
- **Session recovery at app start:** the controller reconciles persisted state and runs the K checks before any launch; unusable/weak config never auto-starts monitoring. **Legacy empty pin in the elevated edition at boot** (`[product, explicit]`): reconciliation shows **Error with a persistent "target confirmation required" indicator** (per the UI state dictionary, independent of `EnableToasts`) — no silent refusal and no silent launch; the user sees why monitoring did not start. **`--background` startup:** when ProcessGuardian starts with the `--background` flag (started to autostart, no main window shown), a reconciliation/hardening **Error is surfaced through the tray** (Error icon state + persistent tooltip/indicator), not a MessageBox — no window steal at logon; the user can open the main window from the tray to see details. *(A one-time migration pinning the legacy hash was considered and rejected: it would silently bless an unverifiable binary, weakening the K policy's fail-closed promise. If ever adopted, its boundary would be a one-time flag persisted next to the pin.)*

**Tests that detect the original defect:** Stop during backoff/verify exits quickly (old: up to 999 s); no launches after a *completed* `StopAsync`; Start during Stop ignored at controller level (not only the UI gate); failsafe cannot start a new session before the old one ends; boot with weak config → Error without launching; **target change via a late debounced save during an active session is rejected at the controller level** (session keeps its original target); **Start with `SaveAsync` throwing → no monitoring starts, no loop engaged.** **Second Start while status is already Error but the cycle task has not exited is rejected** (today `CanStart` is true and that Start re-pins). **Launch-gate race tests are deterministic:** pause after the final hash result but before entering the launch critical section, let Stop close the gate, resume and assert zero `Process.Start` calls; separately hold the launch critical section while the start seam is paused inside it and assert Stop cannot report `RuntimeStopped=true` until the section exits. No launch is permitted after the close linearization point, and none after Stop returns. **Stop during pre-session Start:** a `StopAsync` issued while a Start is still hashing/persisting returns only after the pending work is cancelled/awaited, `RuntimeStopped=true` is guaranteed (no late launch after return), and `SettingsSaved=true` only when `enabled=false` was persisted. If the revert save fails, assert `RuntimeStopped=true`, `SettingsSaved=false`, `SaveFailed` surfaced, and the UI does not present an unqualified successful Stop; the disk may still contain `true`.

### D — store copies and the single writer (same commit as C)

This is not a later increment. It is the persistence half of C+D.

- `LoadAsync` returns an **independent copy** every call; the store **keeps an internal document cache** and returns copies — the point is that no caller can mutate the cached document, not that reads hit the disk every time (numeric re-reads happen every cycle; without the cache that would mean disk I/O every few seconds). `SaveAsync` updates the cache and the store never hands out or keeps a mutable reference to it. The copy is a snapshot taken under the store lock, not the live object the caller can keep mutating.
- **Save mechanism:** **all** VM persistence — including the 500 ms debounce and `FlushNowAsync` — flows **through the controller (or a merge service it exposes)**, never through a separate direct-to-store path. Autostart sync moves with that path; `MainViewModel.FlushSaveAsync` no longer calls `SaveAsync` or `IAutostartService` itself. The controller merges UI-editable fields with current session state in one save, so a stale UI snapshot can never resurrect `enabled=true` after Error, and two "independent copies + full-document Save" races are impossible by construction. **That resurrection test is new:** today's code cannot fail it, because there is only one instance. The test must save a copy that still says `enabled=true` after the controller has already persisted `false`, and assert the disk stays `false`.
- A **committed** path change in the stopped state clears the pin **through the controller**. Keystrokes do not. See Decisions.
- Path+pin immutable within a session (edit forbidden from the moment a session is active); numeric knobs re-read at the top of each cycle (apply next cycle).

**Tests that detect the original defect:** a stale **copy** does not restore `enabled=true` after Error (constructed as two copies, not as today's shared instance); path changed mid-hash keeps the snapshot binding; a committed path change (stopped) clears the pin **via the controller**, and a keystroke does not; numeric change applies next cycle while path+pin stay fixed. The session-cancellation tests are in the C+D list above.

If adopted, enumerate affected surfaces (`ITargetIntegrityService` shape, `WindowsProcessMonitor.StartAsync`, orchestrator call path) and add a test for the hash→launch gap.
- TOCTOU remains **narrowed, not eliminated** — verified file and launched file are linked by name/path only.
- **Boot reconciliation verifies only the saved pin, never re-confirms the binary automatically** (cf. C's reconciliation, E's invalid-path → Error): at boot the controller reconciles against the **saved pin** only — it does **not** silently treat a matching live binary as the user re-confirming/pinning it, and it **never** creates a pin implicitly from a boot-time read in either edition. A non-empty saved pin is always verified (hash); a re-pin/re-confirm is always an **explicit user action** (Stop → Start / re-select). **Auto-resume without a pin is edition-scoped:** in the **elevated** edition, absence of a valid pin + an auto request ⇒ **no launch** (Error/`IsDegraded` per the controller rule, blocked until re-pin); in the **regular** edition, an **empty legacy pin** keeps the **compatibility skip** and monitoring may resume without a pin.
- **Discriminated hash/start result (no nullable-hash / bool-Start ambiguity — fixes K/E/F).** The integrity check / launch gate must return a **distinct result type** (enum/union, e.g. `HashVerifyResult` / `StartResult`), so a `null` hash or `bool Start` can **never conflate "no file" with "read but differs" or "permission/IO failure"**. Mapping:
  - **`Mismatch`** — the file was **successfully read** and its hash **differs from the saved pin** → **fatal** (F: Error, budget-aware). Only this case is a hash mismatch.
  - **`Missing`** — the read yields "no file" (and **not** an access/IO error) → **non-fatal**, `IsDegraded`, **no launch, no budget spent** (E; FR-16). Missing ≠ Mismatch.
  - **`ReadError`** — any failure to open/hash that is **not** a clean missing result (`UnauthorizedAccessException`, I/O error, unreadable object) → **non-fatal**, `IsDegraded`, **no launch, no budget spent** (E's explicit read-error policy), resolved on recovery.
  - **`Cancelled`** — cancellation (Stop/Exit, `CancellationToken`) propagates **as cancellation**, **not** Error and **not** a degraded launch.
  - **Empty/invalid pin is a separate configuration error, edition-dependent:** in the **elevated** edition, an **empty** pin blocks any automatic launch until an explicit re-pin (a config/confirmation state), and an **invalid stored pin** → **Error at boot reconciliation** (C); in the **regular** edition, an **empty legacy pin** keeps the compatibility skip (deferred #5) and is not an automatic fresh-pin trigger, while a **non-empty** pin is verified normally. Pin problems (config) are **never** conflated with target read outcomes — a pin problem is config, a target problem is `Mismatch`/`Missing`/`ReadError`.
  - These types feed the controller's launch/budget decision: `Mismatch` and (for pin) config errors are fatal-capable; `Missing`/`ReadError` spend nothing and never terminate a session; `Cancelled` terminates nothing and publishes nothing.

**Tests:** elevated + empty pin → automatic launch blocked (config error, not `Missing`); **regular + empty legacy pin → compatibility skip (auto-resume without pin) preserved, no pin is created automatically; non-empty saved pin is verified in both editions**; swap between cycles → blocked (`Mismatch`); swap during back-off caught right before launch; **`Missing` ≠ `Mismatch`** — a missing file returns `Missing` (degraded, no budget), a read-but-different file returns `Mismatch`; **permission/IO failure returns `ReadError`, not `Mismatch`**; **cancellation during hash → `Cancelled`, no Error published**; boot with a matching-but-not-pinned binary does not re-pin it implicitly (pin config error, elevated, not a target outcome).

The current code does **not** spend a try here — it fail-closes as a hash mismatch — so this test guards the new non-fatal policy, not a "spent attempt" regression; **(b)** the target is replaced by an unreadable object between the hash and `Process.Start` → `ReadError`, **no budget spent, no fatal** (today this is the same fail-closed mismatch); **(c)** positive control — a genuine started-but-failed launch **does** advance the budget (and only by one). ### F — [defect] Consistent Error semantics
**Files:** `GuardianOrchestrator.cs`, `MainViewModel.cs`, `MainWindow`/tray, `GuardianOrchestratorTests.cs`, `MainViewModelReentrancyTests.cs` (+ result-type mapping in K's contracts)

**Error = a terminated session:** on a fatal cause, **the orchestrator itself exits the cycle loop first** and *then* reports Error (no `await` of the session task from within this call — consistent with C's fatal-error flow). **Order:** the controller **persists `IsMonitoringEnabled=false` first, then publishes Error** on the state channel. Recovery: from Error only **Reset/Start** (fresh session + re-pin); Stop from Error is unnecessary.

**Persistence failure never breaks the lifecycle:**
- On fatal: **session termination and the in-memory desired `enabled=false` are mandatory and final** for this run; the runtime session is dead regardless of disk. `Save(false)` runs **with error handling** (best-effort, EH-01). **Error is published even if `Save` fails**, with a **separate persistence-failure flag** on the state DTO so the UI can show "monitoring off, settings could not be saved".
- **Stale `enabled=true` and the no-durable-latch limitation (honest, not overpromised).** Within the **current process run**, a stale `enabled=true` cannot resurrect the session: the in-memory state is authoritative and the runtime is already terminated. But if `Save(false)` **failed**, the **disk may retain `enabled=true`**, and the plan does **not** promise that the flag alone can never re-enable monitoring at a **future launch**: at the next boot the controller **re-validates against K/E** (it never auto-starts from the flag **alone**) — an invalid/weak retained target yields Error (no silent resume), but a **still-valid retained target+pin with a stale `true` will re-engage monitoring on the next launch** (that is the normal resume path, not a bypass). This is an **explicitly recorded limitation** of the no-durable-latch design: a durable latch (a persisted authoritative "off" state written independently of ordinary settings) would close it and is a possible **future** hardening — **not in scope here**; the plan must not claim it is prevented.
- **Stop = two independent guarantees: `RuntimeStopped` (mandatory) and `SettingsSaved` (best-effort).** `StopAsync` returning successfully **always** guarantees **RuntimeStopped** — the session is cancelled and **no late launch of the target can occur after Stop returns** (the launch gate is cleared with any pending pre-session work), regardless of disk. **SettingsSaved is a separate, best-effort guarantee:** `Save(false)` is attempted and **when it succeeds** the disk holds `false` — and only then may the plan claim "Stop leaves no persisted `true`". **If `Save(false)` fails**, the **in-memory desired `enabled=false` is still set (authoritative for the run), the `SaveFailed` flag is surfaced (J), and the disk may retain `true`** (no-durable-latch limitation above). **No durable latch is introduced — the accepted limitation remains.**
- **Tests `Save throws`** on the **Start**, **Stop**, and **fatal-error** paths: a `SaveAsync` failure must not start monitoring (Start), must not appear as a successful Stop (Stop), and must not suppress the Error publication (fatal); the in-memory session state is authoritative.

**Fatal causes (complete list):** a **hash `Mismatch`** of a successfully-read target (K); a **pin/config error** (empty or invalid elevated pin → Error at boot reconciliation — K/C); **consecutive-budget exhaustion** — the **consecutive** counter `MaxRestartAttempts` reached (a full **window** alone only defers the next relaunch, per I — it does not by itself terminate the session); elevated config in the unsafe-location state (A). **A missing target EXE (`Missing`) and any target read/IO failure (`ReadError`) are NOT fatal** — E keeps FR-16: session stays enabled, `IsDegraded` shown; they never spend the budget and never terminate a session. A missing file does not become fatal at 120 s. **This list is complete** — nothing else terminates a session.

**Not fatal (no time-based escalation of exceptions):**
- **`CheckAsync` exceptions behave like `Unknown`** (per SPEC §7.2.1/EH-02): status stays in the session set, `IsDegraded` set, session stays **alive** — they **never** escalate to Error by time; the loop simply keeps checking. (The E time threshold drives the persistent `IsDegraded` indicator, not an Error transition.) **Today the `catch` in `RunMonitoringCycleAsync` does the opposite:** it sets `Error` and continues with monitoring still enabled. Same for a failed `TryCreate` inside the cycle (a missing file). Both stop being Error. An invalid path **form** is rejected at Start and never becomes a cycle.
- **`StartAsync`/`VerifyStartupAsync` failures spend the consecutive budget only when a real launch ran and failed.** A failure of an **actually-invoked** launch (`Start` executed, then failed to start/verify) increments the **consecutive-failure** counter (`MaxRestartAttempts`, reset on `Running`); it also counts toward the **window** (which counts all automatic relaunch attempts regardless of outcome, per I). The **only fatal consequence is consecutive-budget exhaustion** (`MaxRestartAttempts` reached); a one-off failure that does not exhaust it stays transient, and a full window alone only defers relaunch. **`Missing`, `ReadError`, and `Cancelled` at the launch gate spend neither budget** (per E's budget-charge rule) — a launch that never ran is not a launch failure. There is **no time-based escalation** for these either.
- Consequently the two §9.1 tests asserting `Error` on a throwing check/start are UPDATED as follows:
  - `CheckAsyncThrows_StatusError_LoopContinues` → **`CheckAsyncThrows_SetsDegraded_NoSessionTermination`**: loop continues, status `Monitoring`+`IsDegraded`, and it **never** becomes Error from the exception alone (even after many cycles — EH-02);
  - `StartAsyncThrows_LoopStaysAlive` → **updated**: loop stays alive, restart path continues (`Restarting`), a one-off launch failure is not Error; **repeated launch failures that exhaust the consecutive budget `MaxRestartAttempts` escalate to Error purely via consecutive-budget exhaustion** (budget-escalation test: consecutive-budget exhausted by repeated transient `StartAsync` failures → session terminated Error, flag persisted false; a full window with intervening successful runs does **not** by itself escalate — it only defers the next relaunch, per I);
  - `ShowAsyncThrows_RestartStillSucceeds_StatusMonitoring` stays **unchanged** (notification failures are never Error).
- **FR-14 — the free initial launch is the only exception.** The **initial (free) launch attempt of a session does not consume `MaxRestartAttempts` or the window budget**, whether it succeeds or fails. **Every subsequent *automatic* relaunch attempt spends both budgets** (each spends the consecutive counter if it fails — reset on `Running` — and always counts toward the window), **regardless of outcome and regardless of whether the first attempt failed** (per I: the window counts all automatic relaunch attempts, including after a successful launch and after a target already running at session start). One failed initial launch is not fatal on its own — it only becomes fatal when the subsequent *consecutive* attempts exhaust `MaxRestartAttempts`. **Regression `FirstStart_Free_ThenBudgetConsumed_Error`:** with `MaxRestartAttempts=1`, the free initial launch + one budgeted attempt are allowed; exhausting after that → Error.
- **Manual Stop→Start does not fully close the bypass.** Manual initial launches remain an **explicit exclusion** (per I: free initial launch does not count); the claim that excluding manual Start/Stop fully closes the "reset the counter by toggling" bypass is **removed**. The **history of automatic attempts is preserved** across restart-path cycles (window survives session changes per I), but a manual Start always starts a fresh session whose initial launch is free — so the counter reset by toggling is narrowed, not eliminated (accepted, documented).

SPEC §7.2.1/EH-02 wording is preserved (the loop-outside-Error guarantee holds). Notification failures and user cancellation are also never Error.

**Tests that detect the original defect:** Error → session cancelled + flag persisted false (old: flag stayed on, loop continued); every fatal cause above reaches the same exit; notification failure does **not** disable monitoring; user Stop is never reported as Error. **Persistence-failure tests:** `Save(false)` throwing on fatal → Error published **with** the persistence-failure flag and in-memory `enabled=false`; **limitation test — stale `true` + still-valid retained target at next boot re-engages monitoring** (documents the accepted no-durable-latch behavior, does not claim it is prevented); stale `true` + invalid/weak target at next boot → Error, no silent resume.

### G — [defect + preserve] Deterministic shutdown
**Files:** `src/ProcessGuardian.Wpf/App.xaml.cs`, the shutdown-coordinator helper if extracted, and shutdown lifecycle tests.

For **user Exit**, freeze the ViewModel's edit stream, cancel future debounce scheduling, and obtain a `CommittedSettingsSnapshot` containing the latest committed UI-editable values. The target-path textbox draft is excluded until its explicit commit (Browse, losing focus, or explicit commit); an unfinished path must never be persisted or used to clear the pin. Then call the `StopAsync(snapshot)` contract from C+D: the controller closes the launch gate, terminates the monitoring session, merges that snapshot with controller-owned fields, sets `IsMonitoringEnabled=false`, and persists the merged document in **one settings write**. Do not implement this as a separate UI flush followed by an independently racing Stop save. After inspecting/reporting the typed result, the coordinator removes system autostart per the existing user-Exit semantics, then performs cleanup: `await vm.DisposeAsync()` (disposal only — **no settings save**); `await host.StopAsync(...)`, `host.Dispose()`; `Application.Shutdown()`. A failed settings save does not prevent runtime shutdown or cleanup, but must be surfaced before interactive shutdown completes; it must not be reported as a fully successful persistence operation.

The same combined snapshot + `enabled=false` transaction is used for **user Stop** when a UI snapshot is available, preserving the existing requirement that Start/Stop flush settings immediately. It leaves autostart untouched. Fatal-error handling uses the controller-owned current document and does not depend on a ViewModel snapshot. Every save remains behind the controller/merge service; no shutdown path writes directly to the store.

**Remove the two persistence paths that exist today and contradict this coordinator:**

- `MainViewModel.DisposeAsync` calls `_configStore.SaveAsync(Settings)` unconditionally. Delete that save. Dispose may cancel the debounce, unsubscribe, and flush the log sink. It must not write settings on any exit cause, including SessionEnding. The in-memory model may contain values not yet persisted; **user Exit captures and persists the latest committed snapshot before disposal via the controller**, while SessionEnding intentionally does not. A draft target-path value is not part of that snapshot until committed.
- `App.OnExit`, when `_userRequestedExit` is set, assigns `vm.Settings.IsMonitoringEnabled = false` again after the tray Exit handler has already called `StopMonitoringAndSaveAsync`. Delete that assignment. `OnExit` does not persist and does not mutate the monitoring flag.

**Windows `SessionEnding` is a synchronous WPF event and needs a distinct bridge.** WPF does not await a `Task` returned indirectly by an `async void` event handler; with `Cancel=false`, it proceeds to `Shutdown()` after the synchronous handler returns. Therefore the handler must **not** start an async coordinator and return while it is still running. Before the first await, `SuspendAsync` must synchronously close the launch gate and cancel the session. The `SessionEnding` path then uses one explicit, bounded synchronous bridge to the shutdown coordinator with a **2-second total wait budget** (not a per-step budget; this is deliberately below the usual Windows hung-application prompt threshold); every await on that path must avoid capturing the UI context, and no operation awaited by the blocked handler may require the UI Dispatcher to make progress. If the implementation cannot meet that constraint, use and document a separately tested native session-ending strategy rather than silently fire-and-forgetting an async handler. On timeout, log the incomplete cleanup and continue the OS shutdown path without extending the synchronous wait; do not claim the session task fully completed. The synchronized launch gate from C+D must remain closed even after timeout, so an in-flight hash or delayed continuation cannot later enter `Process.Start`; a last-moment token check alone is not an acceptable substitute. UI-affine synchronous cleanup must execute on its required thread and must not race a still-running coordinator. `Application.Shutdown()` is called explicitly by the user-Exit path; WPF initiates shutdown itself after an uncancelled `SessionEnding` handler returns.

- **Safe by default — changing the monitoring flag and autostart are opt-in per exit cause.** The stop-cause table below is the single source of truth; **no *intent/autostart* write happens beyond the table** on shutdown. (This does not prohibit non-intent writes: **logging and error recording are always allowed**, and the table itself covers fatal-error persistence.)
- **Stop-cause table (what each path does):**
  | Cause | Runtime | `IsMonitoringEnabled` write | Autostart (system task) |
  |---|---|---|---|
  | **User Stop** | terminate runtime | **atomically merge latest committed UI snapshot + save `false`** | **not touched** |
  | **User Exit** | terminate runtime | **atomically merge latest committed UI snapshot + save `false`** | **remove system autostart**, keep JSON `AutostartEnabled` as intent |
  | **Fatal error** | terminate runtime | **attempt to save `false`** (best-effort, error-handled) | **not touched** |
  | **Windows shutdown (SessionEnding)** | terminate runtime | **no write** | **no removal** |
- **Fatal-error persistence is allowed (changed).** The earlier rule "fatal path writes nothing" is wrong for fatal *runtime* errors: on a fatal error the session is being disabled and the runtime may stop, so the app **attempts** to persist `false` (best-effort; a Save failure does not block the Error, see F/C/D). What must stay true: autostart (system task) is **not removed** by either a fatal error or a plain **user Stop** — Stop only disables monitoring, it is not an uninstall/autostart action.
- **Suspend vs Stop (mandatory distinction):** `StopAsync()` cancels the session **and persists `IsMonitoringEnabled=false`** — used for user Stop and user Exit. `SuspendAsync()` cancels the session **without writing the flag** — used for Windows shutdown/logoff (SessionEnding). Without this, a Windows shutdown would persist `monitoring=false` via D's controller single-writer and monitoring would not resume after autostart at next logon. (`StopAsync` is the only flag writer; `SuspendAsync` is the no-write variant.)
- **WM_QUERYENDSESSION → OnSessionEnding → Shutdown (verified WPF behavior; implementation consequence is mandatory).** In WPF, `WM_QUERYENDSESSION` causes `Application.OnSessionEnding` to raise `SessionEnding`; **if the handler leaves `Cancel=false`, WPF calls `Shutdown()` after the synchronous handler returns** (which raises `Exit`). WPF does not await asynchronous work started by an `async void` handler. The synchronous bridge specified above is required; this must not be treated as an ordinary async event callback.
- **Cancelled shutdown guarantee = saved intent, not suspended-forever.** If Windows shutdown is later cancelled, the process **may have already terminated** (WPF's `Shutdown` runs at `WM_QUERYENDSESSION`); there is no "stay suspended until logon" guarantee to promise. The preservation guarantee is the **saved intent** (`IsMonitoringEnabled` and autostart intent left untouched on disk), so the next logon's autostart resumes monitoring. Any true resume-in-process behavior would need an explicit `WM_ENDSESSION` P/Invoke handler — **out of scope, not promised**.
- **Timeouts bound waiting, not completion; no forced cancellation of synchronous Dispose.** A bounded timeout caps how long cleanup *waits*, but it does **not** prove the underlying operation finished — a long synchronous `Dispose` (or a blocked host stop) cannot be force-cancelled. Do not promise cancellation of synchronous `vm.DisposeAsync`/`host.StopAsync`; the timeout only releases the waiting code path and the app reports/logs the outcome (EH-01), never silently continues as if done. This limitation does not relax the launch-gate requirement: for SessionEnding, cancellation/launch-gate closure occurs before waiting, and a timed-out session must not be able to launch later.
- **`OnExit` does no async persistence — single coordinator run only.** All disk writes on user Exit (`Save(false)`, autostart removal) are performed by the **async shutdown coordinator and complete *before* `Application.Shutdown()`** raises `Exit`. The `Exit`/`OnExit` handler is then **only a synchronous, idempotent cleanup safety net** (dispose tray/VM/host if still alive). It must **never re-run an async save** — a second, possibly-racing or partial write to the same file must not be initiated after the coordinator already wrote (a duplicated/racing save could resurrect a value the coordinator had already corrected). If the coordinator never ran (crash path), `OnExit` still must not start a fresh async save — it does best-effort synchronous cleanup and logs, per EH-01.
- **The critical rule is on the disk — no *change to the persisted monitoring intent/autostart*, not "no writes at all":** on the SessionEnding/system-shutdown path, the cleanup must **not change** the persisted monitoring intent or autostart — no `IsMonitoringEnabled=false` write (the intent stays `enabled=true`) and no autostart removal; the persisted `true` and the autostart task/JSON are left untouched. **This is scoped to intent/autostart state**: legitimate writes are still allowed on this path — **fatal-error persistence (best-effort `Save(false)` on a fatal cause, per the table) and logging** are permitted; the prohibition is specifically on *system shutdown-cleanup* flipping the monitoring/autostart intent, which is what would break resume-at-next-logon.
- **Unsaved debounced edits are lost on Windows shutdown only:** the 500 ms debounce and any not-yet-flushed committed UI edits are **not persisted** during a SessionEnding/Windows shutdown (no `FlushNowAsync` or committed-snapshot flush is forced on this path, and `DisposeAsync` must not save either — see the removal above). This is an **accepted loss** — documented, not silently swallowed (EH-01). It does **not** apply to ordinary user Exit, which persists the latest committed UI snapshot through the controller before disposal. An uncommitted target-path draft is not saved on either path.
- **`[preserve]`** user-Exit behavior: autostart is removed on user Exit while JSON `AutostartEnabled` stays as intent; user Stop never touches autostart. `_userRequestedExit` vs system shutdown discriminates per the table.
- **Error/timeout handling for every cleanup step** (not only Stop): each of tray dispose, `vm.DisposeAsync`, host stop/dispose gets a bounded timeout and logs its failure (EH-01) — no step may hang shutdown or die silently.
- Ordering note: J surfaces exit-path errors on top of G's restructured flow (G first).

**Tests:** ordering harness references the full cleanup sequence (tray dispose → VM dispose → host stop/dispose) and asserts `DisposeAsync` performed **no** `SaveAsync`. A regression test fails if `OnExit` writes the monitoring flag or starts a save. **User Exit before the 500 ms debounce fires** persists the latest committed numeric/settings fields and `enabled=false` in one controller/store write; the uncommitted target-path draft is excluded; no late stale debounce save can overwrite it. If this save fails, runtime shutdown still completes, `SettingsSaved=false` is surfaced before interactive shutdown completes, and the UI does not claim full persistence success. Hung session fails fast via timeout (bounded, not forced completion); a `SessionEnding` adapter test proves the handler does not return while the coordinator is still awaited on the successful path, does not deadlock on the UI synchronization context, closes the launch gate before waiting, and prevents a late launch after timeout. A real Windows manual check covers logoff/shutdown because a unit test cannot prove OS event timing. **System shutdown-cleanup leaves the monitoring intent (`enabled=true`) and autostart unchanged** — permitted logging/fatal-error persistence does not count as a system-cleanup intent change; a missing `OnExit` path likewise does not change intent. User Stop persists `false` together with the latest committed settings (or surfaces `SettingsSaved=false`) and leaves autostart untouched; user Exit persists `false` together with the latest committed settings (or reports failure) and removes system autostart only per the exit flow while keeping JSON autostart intent; fatal-error path attempts to persist `false` without touching autostart; `OnExit` after a completed coordinator fires no second async save (single disk write, no racing/duplicate persist) and the Exit handler is only idempotent synchronous cleanup.

### I — [defect] Time-window restart limit: concrete parameters
**Files:** `GuardianOrchestrator.cs`, `AppSettings` (+clamp), `GuardianOrchestratorTests.cs`

- **Default/window:** missing field → safe non-zero default **15 launches / 15 minutes** (sliding window); `0` = off, only when explicitly set.
- **Window duration — constant, not a setting:** 15 minutes is a **compile-time constant**, not a user setting (avoids UI-02 field, clamp/migration concerns, and abuse). If it ever becomes configurable, it joins UI-02 with clamp 1..999 and the 3-char `MaxLength` box (`[product]`, not decided now).
- **Clamps:** the launch-count field clamps to **0..999** (`0` must remain a legal value = limit off). **Combination `MaxRestartAttempts = 0` + window `0`:** explicitly **accepted risk** — both guards off means the user opted out of crash-loop protection entirely; documented in **README/code comment** (not a UI hint, since the window field is not shown in UI-02), not forbidden.
- **Window budget — all budgeted automatic relaunch attempts, regardless of outcome.** The window (`MaxRestartsPerWindow` over 15 min) counts **every** budgeted **automatic (re)launch attempt the guardian initiates** — **whether the launched process then runs, crashes, or the relaunch fails** — including crash-recovery relaunches that succeed, and relaunches performed because the target stopped for any reason. It is **not limited to failed launches** and is **not gated on a prior failed first attempt**: it counts from the session start (the target may already have been monitored as `Running` when monitoring began, then stop and be relaunched). **The only exception is the free initial launch** of a session (FR-14) — one per session is free. A launch **blocked at the gate before an actual launch** (`Missing`/`ReadError`/`Mismatch`/empty-pin config error, or `Cancelled`) does **not** spend the window (E/F). Manual Start→Stop starts a fresh session whose initial launch is free; the automatic-attempt history is preserved across session changes, so toggling is **narrowed, not fully closed** (accepted residual — see F).
- **Two distinct budgets — consecutive (`MaxRestartAttempts`) vs window (`MaxRestartsPerWindow`), separate counters, separate rules.** **(1) Consecutive budget** = count of **consecutive failed** launches; it **resets when the target runs (`Running`)**, per the existing rule — it guards the `launch→immediate-crash` loop. **(2) Window budget** = count of **all** budgeted automatic relaunch attempts (success **or** failure) in the rolling window — it bounds relaunch churn even when each relaunched instance runs briefly. **A full window blocks the next automatic (re)launch attempt but does NOT disable observation of an already-running process:** while the target is `Running`, checking continues normally and only the *next relaunch* is deferred until the window allows it; a full window is not by itself a session Error (Error requires one of F's fatal causes, e.g. repeated *consecutive* failures exhausting `MaxRestartAttempts`).
- **Window survives session changes, and it lives on the singleton.** The window is **not reset** on Start/Stop — a new session inherits the still-open window, so a crash loop cannot be reset by restarting the session (only by time elapsing). The timestamps and window counter are fields of the long-lived DI-registered `GuardianOrchestrator` singleton. They are **not** stored on the controller, per-session object that `Start` creates, or `SessionSnapshot`. A test that Stop → Start within the window still sees the previous launches must fail if the state was reconstructed with the session.
- **A deferred relaunch is visible.** When the window blocks the next automatic launch and the target is not currently running: do **not** enter `Restarting`, do **not** launch, do **not** set `Error`. Keep a session-set status and set `IsDegraded=true` with stable reason `RestartDeferred` (status row and tray tooltip, independent of `EnableToasts`). Clear that reason once a launch is allowed again or the target is observed `Running`. A downed target with a plain `MONITORING` label and `IsDegraded=false` fails review.
- **Window does NOT survive process restart — accepted limitation:** the window's launch timestamps are **not persisted** across a ProcessGuardian process restart; the window lives only while the app runs (a restart resets the budget, so a crash-looping target can outlast the guardian by never outliving a single process run). Persisting timestamps (protected ProgramData storage + migration test) is a possible future hardening, **not** in scope — the limitation is documented and accepted. (This mirrors A/L's ProgramData trust model if ever adopted.)
- **settings.json field:** new field **`MaxRestartsPerWindow`** (int, default 15 when absent, `0` = off). It is **not shown in UI-02** (the 15-minute window duration is a compile-time constant, and the count is an internal safety net, not a user knob).
- **Monotonic time is mandatory:** inject `TimeProvider`, record launch timestamps using `GetTimestamp()`, and calculate elapsed/window membership with `GetElapsedTime()`. Do not use `DateTimeOffset.UtcNow`, wall-clock timestamps, or `GetUtcNow()` to decide whether a launch has aged out of the sliding window; clock corrections/time-zone changes must not extend or prematurely expire the in-process window. This is an in-memory-only window (it intentionally resets when the ProcessGuardian process restarts, per the accepted limitation above).
- **Tests use managed time** (injectable `TimeProvider`) — no real sleeps; use a fake provider with independently controlled monotonic timestamps and assert that advancing wall-clock time alone does not age out a launch.
- Interaction with `MaxRestartAttempts=0`: window still applies unless explicitly `0` (documented interplay). Also fixes the stale `HugeCheckInterval_DoesNotBusyLoop` comment (fold-in from Deferred #4).

**Defect-detecting tests:** repeated crashes with brief recovery exhaust the window (old: unbounded); legacy config missing the field gets the safe default; **FR-14 regression `FirstStart_Free_ThenBudgetConsumed_Error`** — the free initial launch does not consume the window; **window counts successful relaunches too:** successful initial launch → repeated crash/recovery with **successful verification on each recovery** (each recovery relaunch is a budgeted attempt) → the next automatic relaunch **beyond the window limit is blocked/denied**, while observation of an already-running period continues; **target already `Running` when the session begins** → when it later stops and is relaunched automatically, that relaunch **is a budgeted window attempt** (the window counted from session start, not from the first failure); **full window while the target is currently `Running`** → no relaunch is attempted (blocked), monitoring/checking is **not** disabled, only the next launch is deferred, and `IsDegraded` is **not** raised merely because the running process is inside a full window; **full window while the target is down** → no relaunch, status stays in the session set, `IsDegraded` with reason `RestartDeferred`. Stop → Start inside an open window does not clear the timestamps.

## 2. Accepted product decision: automatic removal of elevated autostart after config quarantine

### 2.1. New recovery policy

When elevated configuration recovery quarantines an untrusted config and creates fresh defaults, the app must automatically converge to the following final state:

- scheduled task `AppEdition.ScheduledTaskName` is **absent**;
- persisted `AutostartEnabled=false`;
- persisted `IsMonitoringEnabled=false`;
- target path and target hash pin remain empty until the user selects a target and explicitly starts monitoring;
- the HKLM recovery journal no longer contains `ResetNoticePending`;
- ordinary settings editing, manual Start, and the autostart checkbox become available only after the recovery transaction has been fully verified.

The product no longer offers a “keep autostart” choice. Recovery always removes the elevated scheduled task. After recovery completes, the user may manually enable autostart again using the ordinary checkbox. Enabling it must use the existing verified scheduled-task registration path and the current executable path.

This is an intentional product-semantics change accepted by the user on 2026-11-02. It is not an implementation shortcut and must not be silently reverted to the old A/B flow.

### 2.2. Startup ordering and controller ownership

- `ResetNoticePending` is detected before ordinary startup autostart synchronization and before any monitoring session can start.
- While recovery is pending, **no startup sync may create or re-enable** the scheduled task, even if an unexpected/stale settings snapshot contains `AutostartEnabled=true`.
- The application must not start monitoring while the recovery transaction is incomplete. `StartAsync` and any other entry point that can create a session must reject the request while recovery is pending. The UI command must also be disabled; controller enforcement is authoritative.
- The recovery operation is owned by the Application/controller layer, not by XAML code or an independent ViewModel writer. The composition root may initiate the controller's startup reconciliation, but no second settings writer is introduced.
- The task name must come from `AppEdition.ScheduledTaskName`; do not duplicate or hardcode a different task name in the Admin-specific recovery path.

### 2.3. Idempotent delete-and-verify transaction

The previous implementation first queried task state and refused to execute Delete when the query returned `Unknown`. That prevents recovery in the observed case. Under this amendment the desired result is unconditionally “task absent”, so a successful pre-query is **not a prerequisite to attempting the exact task deletion**.

Required transaction:

1. Invoke `schtasks.exe /Delete /TN "<AppEdition.ScheduledTaskName>" /F` using the existing absolute System32 executable path. This is narrowly scoped to the one application-owned task name.
2. Capture the process exit code, standard output, standard error, and invocation exception separately. Do not collapse stdout/stderr before diagnostics are recorded.
3. Do not treat Delete exit code 0 as proof that the task is absent. Do not treat a nonzero exit code as proof that it remains present or is absent.
4. Query the exact task after the delete attempt and verify the resulting state. Only a positively verified `Absent` state satisfies the scheduler part of recovery. A still-present task, access denial, unavailable Task Scheduler service, process invocation failure, unparsable/unverifiable result, or any other `Unknown` result leaves recovery pending.
5. A task that was already absent is a successful idempotent outcome only when absence is positively verified. If `/Delete` reports a not-found error, still verify absence; do not rely on the delete message alone.
6. Once task absence is verified, persist the recovery settings with `AutostartEnabled=false` and `IsMonitoringEnabled=false`. Confirm the actual save result.
7. Only after both scheduler absence and settings persistence have succeeded may the app clear `ResetNoticePending` in the HKLM journal.
8. If any operation fails, leave `ResetNoticePending` intact, do not enable/recreate autostart, do not start monitoring, and record the exact failed step. A later startup retries the same idempotent operation.

**Crash/retry semantics:** every step must be safe to repeat. A crash after task deletion but before settings save or journal acknowledgement must resume by verifying/deleting the same task, persisting `false`, and clearing the journal. A crash after settings save but before journal acknowledgement must not recreate the task. The recovery latch is cleared last.

### 2.4. Bounded retry and unresolved recovery

- Perform a small bounded number of attempts during one startup (maximum **3** delete/verify attempts, with bounded delays; do not create an infinite retry loop or block the UI thread).
- If all attempts fail, leave the journal pending and keep the application in standard `STOPPED` state. The app must not auto-start monitoring and must not enable the autostart checkbox or Start command.
- Detailed cause, exit codes, and captured command output must be recorded in the normal log. Do not show a recovery modal, a long guidance paragraph, or a dedicated recovery toast.
- A subsequent application start retries recovery. Do not add an unbounded background retry service unless separately approved.
- Normal user settings may not be used to bypass the pending recovery gate. In particular, manual Start must remain blocked until the scheduled task is verified absent and the journal is cleared.

### 2.5. Task Scheduler diagnostics (required because of the 2026-11-02 manual failure)

The manual Admin run reached `/Query` exit code `1`; the current log omitted the process output, so the cause is not yet known. The implementation must make this diagnosable before claiming the live issue is fixed.

- Preserve separate `ExitCode`, `StandardOutput`, and `StandardError` in the command result/seam.
- For nonzero query/delete results, log the operation, exit code, exception type/message if invocation failed, and bounded/sanitized stdout/stderr. Set a conservative size cap (for example 4 KiB per stream); never dump a successful full task XML document or unrelated file contents into the log.
- Distinguish at least: verified task-not-found, access denied, Task Scheduler service unavailable, executable invocation failure, malformed XML, task still present/misconfigured, and unknown/unclassified failure.
- `Unknown` must remain fail-closed. Do not “fix” the current error by treating every exit code `1` as task absent or by weakening the XML checks for `Command`, `Arguments`, `LogonTrigger`, `LogonType=InteractiveToken`, or `RunLevel=HighestAvailable`.
- If not-found detection still depends on localized output, support only concrete, tested messages for supported Windows locales and record an `Unknown` state for anything else. Add fixtures based on actual captured output from a Windows run once available; do not label hand-authored “real XML” fixtures as live Windows validation.
- Keep command invocation through the absolute `%SystemRoot%\System32\schtasks.exe` path.
